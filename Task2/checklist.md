# Задание 2. Проверочный лист безопасности бизнес-систем

## Какие системы проверяем

| Группа | Системы | Что важно проверить |
| --- | --- | --- |
| Продажи | Витрина продаж, `client-crm-app`, `client-tour-app`, `client-mart-app`, `client-mart-estate-app` и их БД | Персональные данные, бронирования, результаты осмотров и сделки. Нужно исключить показ чужого профиля и согласовать регистрацию клиентов между приложениями. |
| ЖКУ | Мобильная витрина собственников, `tenant-core-app`, CRM собственников и их БД | Доступ к данным квартир, платежам, сообщениям и ремонту должен соответствовать собственнику и его УК. Управление устройствами квартиры требует отдельной проверки прав. |
| Финансы | `accountant-service-1`, его БД и служба каталогов | Доступ к бухгалтерским данным, права сотрудников и сохранность записей. |
| Обработка данных | Хранилище Greenplum, S3, BI и отчётность | В хранилище поступают сырые данные из бизнес-систем. Нужно ограничить доступ к ним и проверить состав выгрузок. |
| Вход пользователей | Keycloak, Active Directory и связанные хранилища учётных записей | Проверка личности пользователя, управление его учётной записью и правами. Наличие этих систем само по себе не подтверждает правильность настройки доступа. |
| Внешние взаимодействия | API управляющих компаний, платёжная система, государственные регистрационные органы | Проверка прав партнёров и состава передаваемых данных. Ошибки доступа прямо описаны для API УК; состояние остальных интеграций нужно уточнить. |

## Почему выбраны эти разделы

| Раздел                             | Обоснование                                                                                                                                                                                                                                                       |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| I. Управление доступом             | Уже есть жалобы на чужие данные в личном кабинете. Партнёры могут просматривать и изменять данные другой УК, а в системах обработки данных отсутствуют ограничения доступа к данным. Это приоритетные проверки.                                                   |
| II. Безопасность данных            | Регистрация клиентов ведётся в нескольких несогласованных точках, а потоки между продуктами контролируются несистемно. Это мешает обслуживанию клиентов и развитию BI, ML и AI. Проверки должны охватить качество данных, их передачу, хранение и восстановление. |
| III. Защита инфраструктуры         | Компания использует собственный ЦОД, приватное облако и мощности провайдера, в том числе для разработки и тестирования. Нужно проверить защиту внешнего входа, связи между системами и работу с данными в разных средах.                                          |
| IV. Управление инцидентами         | Специалист по ИБ один, и до него доходят не все изменения. При этом проблемы доступа уже замечены пользователями и разработчиками. Нужно проверить, как такие случаи выявляют, исправляют и учитывают при изменениях систем.                                      |
| V. Безопасность внешних интеграций | Этот раздел добавлен вместо общего списка специфических вопросов шаблона. Работа API УК прямо названа проблемой, а компания планирует расширять партнёрские сервисы. Поэтому проверка прав партнёров и передаваемых данных очень важна.                           |

### V. Безопасность внешних интеграций

Этот раздел добавлен вместо общего списка специфических вопросов шаблона. Работа API УК прямо названа проблемой, а компания планирует расширять партнёрские сервисы. Поэтому проверка прав партнёров и передаваемых данных очень важна.

| №   | Вопрос                                                                                      | Статус     | Комментарий                                                                                                                                                                                             |
| --- | ------------------------------------------------------------------------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Есть ли единые правила безопасности для API управляющих компаний?                           | Нет        | В контексте прямо указано, что API используются без единых политик безопасности.                                                                                                                        |
| 2   | Может ли партнёр работать только с клиентами и ЖК своей УК?                                 | Нет        | Описана возможность просмотра и изменения данных другой управляющей компании. Проверять нужно и чтение, и изменение.                                                                                    |
| 3   | Контролируется ли, что через API передаются только необходимые для бизнес-процессов данные? | Нет        | По описанию системный контроль передаваемых данных отсутствует. API содержат персональные данные, поэтому рекомендуется проверить необходимость каждого передаваемого поля и исключить лишние сведения. |
| 4   | Проверяется ли безопасность новой интеграции и изменений её API до запуска?                 | Нет данных | Не все изменения доходят до специалиста ИБ; отдельный обязательный порядок проверки интеграций не описан.                                                                                               |
| 5   | Можно ли определить партнёра по его учётным данным и отдельно отозвать его доступ?          | Нет данных | Способы входа партнёров, разделение их учётных данных и отзыв доступа нужно уточнить.                                                                                                                   |
| 6   | Проверяются ли попытки получить или изменить чужие данные при тестировании API?             | Нет данных | Разработчики замечали нарушения доступа, но наличие регулярных проверок с пользователями разных УК не подтверждено.                                                                                     |
| 7   | Проверяются ли источник, корректность и повторное получение сообщений об оплатах и сделках? | Нет данных | Интеграции с платёжной системой и госорганами есть. Обработка ошибочных, поддельных или повторных сообщений не описана.                                                                                 |

## Что проверить и исправить в первую очередь

1. Найти причину показа чужих данных в личном кабинете и закрыть доступ партнёров к чужим УК.
2. Ограничить доступ к данным в хранилище и BI в соответствии с рабочими задачами.
3. Согласовать регистрацию клиентов и правила передачи данных между системами и партнёрами.
4. Восстановить передачу изменений специалисту по ИБ и определить порядок проверки новых интеграций.
5. Собрать подтверждения по пунктам «Нет данных».
